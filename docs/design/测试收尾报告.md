## 1. test_sync_hooks.gd `_test_player_speed`（3 个失败）→ 断言漂移，已修复

### 1.1 失败现象

```
[TEST] FAIL: player speed agg wrong (312.00)
[TEST] FAIL: speed cap not applied (400.00)
[TEST] FAIL: wind_speed_cap_bonus not raising cap (500.00)
```

测试期望 343.2 / 440 / 550（按旧基准 220），实测 312 / 400 / 500。

### 1.2 判断：断言漂移（balance.json 是正确的）

- `data/balance.json` 的 `player.speed` 已改为 **200**（player.gd `_move_speed()` 从 `GameState.balance().get("player", {}).get("speed", ...)` 读取，与测试同源）。
- 实测值与 200 基准完全吻合：
  - `200 × (1+0.1+0.2) × 1.2 = 312` ✓
  - `200 × (1 + min(1.6, 1.0)) × 1.0 = 400` ✓（默认 cap 1.0）
  - `200 × (1 + min(1.6, 1.5)) × 1.0 = 500` ✓（风行者 cap 1.5）
- 聚合公式、上限截断、cap 提升三条链路本身工作正常，失败纯粹是断言里的旧常数 220 未随 balance 同步。

### 1.3 修复（test_sync_hooks.gd）

按任务建议的“更稳健”方案：不再硬编码 220，基准移速从 balance.json 读取（与 player.gd 同源），期望值按公式计算：

```gdscript
var base_speed: float = float(GameState.balance().get("player", {}).get("speed", 220.0))
# 断言分别改为 base_speed * 1.3 * 1.2 / base_speed * 2.0 / base_speed * 2.5
```

今后 balance 再次调整移速时测试自动跟随，不再产生同类漂移。

## 2. test_core_shell.gd：frenzy / mana_echo 原生回退（2 个失败）→ 断言漂移，已修复

### 2.1 失败现象

```
[TEST] FAIL: frenzy must fall back to native (no shell), got <null>
[TEST] FAIL: mana_echo must fall back to native (no shell), got <null>
```

### 2.2 排查

测试的确定性验证段：

```gdscript
GameState.tables["spells"]["cores"] = [entry[1]]   # 只剩 frenzy / mana_echo
var c2: Dictionary = GameState._make_spell_choice()
# 期望 id 以 "frenzy:" / "mana_echo:" 结尾（原生无外壳）
```

对照 `game_state.gd._make_spell_choice()` 当前实现（08-12 元素门控新增）：

```gdscript
var eligible: Array = []
for c in cores:
    var el := str(c.get("element", ""))
    if el == "" or el == "blade" or holdings.has(el):
        eligible.append(c)
if eligible.is_empty():
    return {}          # ← 门控把空池直接打成空选项
```

- `_element_holdings()` 只统计 `run.items` 元素/流派 tag + `run.grid` 核心元素。
- spells.json 中 `frenzy.element = "buff"`、`mana_echo.element = "void"`；测试运行时 run 里没有任何 buff/void 持有 → `eligible` 为空 → `_make_spell_choice()` 返回 `{}`（id 为空，`<null>`）→ 断言失败。

`_invalid_combo` 对 frenzy/mana_echo 的过滤矩阵本身正确（`frenzy`/`mana_echo` 标志位 → 全部外壳 return true），失败完全由门控前置过滤引起。

### 2.3 判断：断言漂移（游戏代码行为正确）

元素门控是 v48/v49 的设计决策（“未持有某元素不出该元素法术”），代码正确；是测试没同步 08-12 门控语义，属于测试期望过时。

### 2.4 修复（test_core_shell.gd）

确定性验证前把两个核心放入 `run.grid`（语义：玩家已持有这两个核心 → 元素被持有 → 门控放行），结束后恢复：

```gdscript
var saved_grid: Array = GameState.run.get("grid", [])
GameState.run.grid = [{"core": "frenzy", "shell": ""}, {"core": "mana_echo", "shell": ""}]
# ...原循环不变...
GameState.run.grid = saved_grid
```

修复后两用例通过（`spell_part:frenzy:` / `spell_part:mana_echo:` 原生回退成立）。

## 3. test_core_shell.gd：whirl split（1 个失败）→ **真 Bug（projectile 对象池竞态），不改测试掩盖**

### 3.1 失败现象

```
SCRIPT ERROR: Trying to assign invalid previously freed instance.
   at: obtain (res://scripts/combat/projectile.gd:125)
SCRIPT ERROR: Invalid access to property or key '_hit_enemies' on a base object of type 'Nil'.
   at: _spawn_split_minis (res://scripts/combat/projectile.gd:572)
[TEST] FAIL: whirl split: expect 2 minis, got 0
```

### 3.2 根因（已用池内探测逐帧实证）

1. 弹幕对象池（6921478 引入）中，**同时被 `queue_free` 又在物理帧内回收的弹体会向池里写入死引用**：
   - 弹体在场上时被 `queue_free()`（测试的 `_clear_projectiles` 与生产代码 `clear_player_projectiles`（换法术/换网格）行为一致）；
   - 但 `queue_free` 的销毁发生在**帧末**，销毁前该弹体仍会跑 `_physics_process`；
   - 瞬发核（毒雾 speed=0）下一物理帧 `_explode_at()` → `_retire()` → `recycle(self)` → **remove_child 后正常入池（此刻 valid）**；
   - 帧末 pending 的 `queue_free` 生效，把池中条目销毁 → **池中残留“已释放实例”引用**。
2. `obtain()` 的取池循环对死引用**不健壮**（projectile.gd:125）：

   ```gdscript
   var cand: Node = _proj_pool.pop_back()   # 类型化赋值：弹到已释放实例 → 报错并中断函数
   if is_instance_valid(cand): ...
   ```

   GDScript 把“已释放实例”赋给类型化 `Node` 变量属于硬错误：**报错后 obtain() 直接中断返回 null**，既没有继续弹下一个候选，也没有走 `instantiate()` 兜底。
3. 于是 `_spawn_split_minis`（projectile.gd:559）拿到 null → :572 访问 `_hit_enemies` 报 Nil → **0 个小弹生成** → 测试失败。

实测证据（test_core_shell 内插桩，`_proj_pool` 内容 dump）：

```
[DBG] pool after cast:  stats={created=3, reused=1, idle=0}  entries=[]
[DBG] pool after end clear: stats={created=4, reused=1, idle=3} entries=[DEAD, DEAD, DEAD]
[DBG] pool pre-split: stats={created=4, reused=1, idle=4} entries=[DEAD ×4]
```

池条目由 valid 变 DEAD 恰好发生在“被 queue_free 的毒雾回收”之后——竞态坐实。git HEAD 基线复现一致（批次 A 结论确认）。

### 3.3 影响面（不止 whirl split）

任何一次 `obtain()` 撞上死引用都会中断，**导致该次法术/分裂静默失效**（生产路径：施法后立刻换法术 → 场上毒雾/瞬发核被 `clear_player_projectiles` queue_free → 下一帧回收进池 → 帧末销毁 → 池污染 → 下次施法 obtain 报错中断）。对象池复用率越高、弹幕越频繁，越容易命中。

### 3.4 建议修复（交给主 agent 派修复任务，本次未改游戏代码）

- `projectile.gd::recycle()`：入口加 `is_queued_for_deletion()` 守卫——被 queue_free 的弹体不再入池（直接放行销毁），从源头杜绝死引用入池。
- `projectile.gd::obtain()` 取池循环改为非类型化取值 + 显式校验，保证死引用只被跳过、永不中断：

  ```gdscript
  while not _proj_pool.is_empty():
      var cand = _proj_pool.pop_back()      # 不要类型化 Node，避免赋值硬错误
      if is_instance_valid(cand):
          proj = cand
          _proj_reused += 1
          break
  ```

- 可顺手在 `clear_player_projectiles()` 里对已 `is_queued_for_deletion()` 的弹体跳过 `queue_free`（防御性），以及复查 `_reset_for_pool()` 里 `vseed.queue_free()` 与复用时序。
- 修复后 `_test_whirl_split_speed` 现有断言即应通过（小弹 2 只、速度 ≥240、root=1.5 继承均与实现一致），无需改测试。

## 4. 排查中发现并修复的 2 个既有偶发（非任务列项，影响"全绿"稳定性）

### 4.1 test_core_shell `_test_summon_rapid` 偶发："expect 3 summons, got 4"（约 1/5~1/8）

- **根因（get_stack 实证）**：测试创建的 `caster`（`SPELL_CASTER_SCRIPT.new()`）是**活节点**，
  其 `_physics_process` 会按 `GameState.run.grid` 自动施法（spell_caster.gd:35-52）。测试在
  2 个 `process_frame` 等待期间 caster 存活，自动施放了随机开局技能；当开局网格（autoload
  `new_run` 随机 `_roll_starter_grid`）抽到 `summon_bat×rapid`（shots=3）时，多召 3 只蝙蝠，
  bat `max_count=1` 存活 1 只 → 组内 4 只。非断言漂移、非本次改动引入（对照组撤掉改动后仍复现）。
- **修复（test_core_shell.gd）**：该用例只验证 `_spawn_summon` 直调语义，临时清空
  `GameState.run.grid`（结束后恢复），杜绝活 caster 自动施法干扰。修复后 0/15 复现。

### 4.2 test_sync_hooks `_test_crit_g3` crit_crit_bounce 偶发："ricochet not spawned"（约 1/4~1/8）

- **根因（池插桩实证）**：弹射弹在敌人位置生成（obtain 同步入组，created=1），下一物理帧即
  命中源敌人并回收（idle=1、group=0）。测试在 `await process_frame` **之后**才查组，偶发撞上
  "已合法回收"，误判为未生成。属断言时机竞态，非游戏 bug（弹射弹确实生成了）。
- **修复（test_sync_hooks.gd）**：obtain 为同步入组，`_trigger` 返回时弹射弹必在组内，
  改为**立即断言**（去掉先 await）。修复后 0/12 复现。
